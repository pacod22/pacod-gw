# Threat model

This is the threat model of concept section 16, checked against the code as it is built.
Each row says what protects against the threat, where that lives, and what risk remains.
Signing in through pacod-id (`PGW_AUTH=oidc`) has rows of its own below; pacod-id's own
threat model is `vendor/pacod-id/docs/threat-model.md`.
Reports of weaknesses go to the contact in [SECURITY.md](../SECURITY.md).

## What is worth protecting

- **Provider keys.** Every provider account of the installation. Whoever has one spends
  money in its name and can reach the files and batches stored with it.
- **Prompts and answers.** They pass through every gateway, and audit mode stores them.
- **Gateway keys and console sessions.** Whoever holds one acts as that workspace or user.
- **pacod-id's accounts and signing keys** (with `PGW_AUTH=oidc`). Whoever can sign a token
  pacod-id's way, or holds an account's password, acts as anyone in the gateway's realm.
- **Tenant separation.** What one workspace sends, stores, spends and reads must stay its
  own.
- **The accounting.** Usage, cost and limits must be right, so that limits hold and bills
  can be trusted.

## Who and what is trusted

| Party | Trusted for |
|---|---|
| Callers with a gateway key | Nothing beyond their key's workspace, modes, models and limits. |
| Console users and admin tokens | What their roles allow (concept 5.4), nothing more. |
| Operators of the host or cluster | Everything. They hold the key-encryption key and the databases. |
| Providers | Their own answers. Their error messages are passed on. |
| The analytics service | Its own database. It parses pages from outside (price sources), so it holds no provider keys, and its token opens only the job endpoints of the core. |
| pacod-id | Who people are and which roles they hold, with `PGW_AUTH=oidc`. The core takes its tokens and its feed of roles as true. It holds the gateway's key pepper (`PID_LEGACY_PEPPERS`), and with it the HMAC key of the gateway keys. |
| PostgreSQL and ClickHouse | Storage. They hold only encrypted provider keys and keyed hashes of gateway keys. In compose, the same PostgreSQL server also holds pacod-id's database, with password hashes and sealed signing keys (see "The gateway's database role reading pacod-id's tables"). |

## Threats and controls

| Threat | Control as built | Remaining risk |
|---|---|---|
| Provider keys stolen from storage | Envelope encryption: an AES-256-GCM data key per credential, wrapped by the key-encryption key, with the credential id bound in (`crypto/envelope.rs`). The key-encryption key comes from the environment or a file (`PGW_KEK`, `PGW_KEK_FILE`, `PGW_SECRETS_DIR`), never from the database, and backups leave it out (`deploy/scripts/backup.sh`). Rotation: `PGW_KEK_OLD` and `rewrap-secrets`, which refuses while an instance has not confirmed the new key. | With compose the key-encryption key sits in `deploy/.env` on the same host as the database. Keep that file and the backups apart; with Helm use a Secret or a mounted file. |
| A service account's key stolen or misused | A key file is checked when it is added (a service account of `googleapis.com`, an RSA key of at least 2048 bits, at most 16 KiB) and stored like any provider key; reads show the account and the key id. The key never leaves the gateway: it signs a token request, which goes to `https://oauth2.googleapis.com/token` only. The key file's `token_uri` is ignored, so a crafted file cannot send the signed request elsewhere (`PGW_GOOGLE_TOKEN_URL` overrides the address for tests only). Access tokens live in each instance's memory, are never logged, and are dropped after a 401. A key file is refused as an API key, and an API key as a key file. `make smoke-live` scans the logs for private keys and Google access tokens as well. | The token is a bearer token for everything the account may do in its project: IAM is the boundary. Give the account Vertex AI User on one project only. An organisation admin who adds a credential of the organisation's own brings their own project and its risks. |
| A shared Vertex AI token reaching more than one model | Proxy mode to Vertex AI allows POST only, to the provider's own project and location (or express mode's path), to the model methods only, with no `%`, `..` or `//` in the path and no query but `alt=sse`; the caller's Google headers (`x-goog-user-project` would bill another project) and method overrides are removed. The model in the path must be in the repository and granted, as for every proxy call. On the installation's shared credential, Cloud Storage objects (`gs://`), `projects/…` resources and retrieval from the project's data stores are refused (403 `own_credential_required`), and model routing (`routingConfig`), which would let Vertex AI choose a model, is refused on any credential. The Gemini interface never takes the caller's project or location: the upstream address is the provider's. | A model method of a granted model can still reach what that model reaches inside the project (tuned versions, Model Garden deployments of the same id). |
| Provider keys leaked through the API or logs | Secrets are write-only; reads show a fingerprint (the last four characters and a hash prefix). The audit log stores hashes of documents, not documents. Configuration exports leave secrets out. The caller's gateway key is never forwarded. `make smoke-live` scans every log for the provider keys it used. | The provider's own error text is passed on, up to 300 characters, and stored in the usage event's `error_message`. A provider that echoed a key would leak it; none is known to. |
| Gateway keys in logs | Keys are not logged by the gateway. Caddy redacts `Authorization` itself, and its access logs on the API host drop `X-Api-Key` and `X-Goog-Api-Key` (`deploy/caddy/Caddyfile`). Google's SDKs may send the key as `?key=` in the URL: proxy mode and the Gemini interface accept a gateway key there and remove it before anything reads the URL (the call is not forwarded with it, nor written to the audit record or to an attempt's URL; the Gemini interface records its paths as a template), and Caddy drops the `key` query parameter from its access logs. A `key` that is not a gateway key is the provider's own and is forwarded. | A load balancer or proxy of your own in front of Caddy must do the same, for the query string as well. |
| Guessing or flooding gateway keys | 32 random bytes per key; lookup by HMAC-SHA256 with a pepper, no slow hash; malformed keys are refused before hashing. Failed attempts are limited per client address (60 a minute) on the data plane and for admin tokens. With `PGW_AUTH=local`, logins lock an account after 10 failures in 15 minutes, and unknown accounts take as long as known ones; with `PGW_AUTH=oidc` password guessing and lockout are pacod-id's (its threat model). | The failure limit is per instance and per exact address; a client with many addresses (an IPv6 /64) gets more tries. A key's 256 bits make guessing hopeless anyway. Anyone who knows an email address can lock that account for 15 minutes. |
| Management API exposed | Its own listener, not served by `--role gateway`. Compose publishes no core port, and the backend network is internal; Helm's network policy lets only the console, analytics and tester reach the admin port. With `PGW_AUTH=local`: passwords use Argon2id; sessions (`pgws_`) are random tokens stored as hashes, ended by logout and by a password change; the console keeps the token in an httpOnly, SameSite=Lax cookie. With `PGW_AUTH=oidc` the rows below apply and `pgws_` tokens are refused. Either way the console relies on SvelteKit's origin check against cross-site form posts. | The console sends no Content-Security-Policy. |
| Server-side request forgery through admin-supplied URLs | Provider URLs and price sources are checked when saved, and every connection is checked again after name resolution (`pacod-gw-events/src/egress.rs`). Refused: private, loopback, link-local (cloud metadata), carrier-grade NAT, reserved and documentation ranges, and IPv6 forms that lead to them (IPv4-mapped and -compatible, NAT64, 6to4, Teredo, site-local). `PGW_EGRESS_ALLOW_PRIVATE` opens named hosts or ranges, such as a local Ollama. Price pages are fetched by the analytics service, which re-checks every redirect. | Alert webhooks come from the operator's settings and are not checked. |
| A compromised analytics service | It holds no provider keys. Its internal token opens only the job endpoints of the core (lease, result, extraction); it is not accepted as a principal of the management API. | Through the extraction endpoint it can have the `_system` workspace call a model, and its job results can propose or, within the auto-apply bound, change prices. |
| One workspace reading another's data | The workspace comes from the key, never from the request. Every report goes through the core, which replaces any scope the caller sent with the scopes their roles allow. The `/events` stream carries only changes of scopes the caller may read. | Prometheus metrics carry organisation and workspace labels, and the metrics port has no authentication: whoever reaches Prometheus or Grafana sees usage of every tenant. Keep them to operators. |
| One workspace using another's files or batches | Files and batches created through the gateway are recorded with their workspace (`dataplane/objects.rs`); lists show a workspace's own, and other ids answer 404. A body that names a `file_id` is checked against that record in both modes, with escaped and repeated keys read as the provider reads them; on the shared credential an unknown id is refused too (`dataplane/files.rs`). | On a workspace's or organisation's own credential an unknown id passes, a blind relay is not read, and proxy-mode file and batch paths are relayed unrecorded. Workspaces that share an organisation's credential are therefore separated only for what goes through the managed endpoints. Gemini's files (`fileData.fileUri` naming the Files API), context caches (`cachedContent`) and file search stores (`fileSearchStoreNames`) are not recorded per workspace: on the installation's shared credential they are refused in both modes and on the Gemini interface (403 `own_credential_required`), in either spelling of their keys, on an own credential they pass. Other providers' file ids are not checked. |
| A caller making the provider reach servers of its choosing | Provider tools (web search and fetch, code execution, the MCP connector, Gemini's grounding) are allowed per workspace by type, checked on the body the provider receives in both modes (`dataplane/tools.rs`). A `tools` list the gateway cannot read is refused when a workspace restricts tools, and blind relay is refused there. A Gemini tool entry with a key the gateway does not know (`googleMaps`, `fileSearch`, a later one) counts as a provider tool of that name, so a restricted workspace must allow it by name. | No restriction by default: a workspace, its organisation or the global settings must set the list. |
| A forged reasoning history | Reasoning another provider produced is removed before Claude sees it, and each provider gets back only signatures with its own origin prefix (`gw1.gemini.`, `gw1.vertex.`). A Gemini caller holds other origins' signatures wrapped in base64; unwrapped, a signature still goes only to the provider of its origin, which checks it. When a caller drops a Gemini thought signature in the current turn, the translated route sends Google's placeholder `skip_thought_signature_validator`, so the turn is not refused. | With the placeholder Gemini does not check that the earlier function call was its own: a caller can put a made-up call and result into the conversation. That is no more than a caller can do with any provider that has no signatures. |
| A caller getting past what a template or the capability profile sets | The gateway writes the limits, sampling and reasoning itself; `provider_options` and the members a Gemini caller passes through never set them (they are left out and named in `dropped_params`). Gemini's second spelling (`generation_config`, snake_case members) is read as one with the first, in managed mode and for proxy-mode templates, so a limit cannot be passed by spelling it the other way. | Proxy mode without a template governs nothing, by design. |
| Disagreement between gateway and provider about a request | Bodies are checked as strict JSON (`json/scan.rs`); any repeated top-level key is refused in both modes. Objects the gateway writes into must not repeat keys either. | Repeated keys deeper in a translated body keep their last value. |
| Calling a model server directly | Not provided by the deployment files: neither compose nor the Helm chart contains a model server. | A local model server must be reachable only from the gateways: its own network in compose, or an egress and ingress policy in Kubernetes. |
| Prompts in telemetry | Logs, spans and usage events carry metadata only: model, tokens, timing, ids, tags. | `error_message` can quote request content when a provider's error does. |
| Stored prompts and answers (audit mode) | Off by default; an organisation can forbid or require it. Credential headers are stored by name only, and the gateway key by its id. Only admins and auditors of the scope read records; reading, exporting and deleting them is written to the audit log. Records expire (14 days by default) and are deleted by ClickHouse. | Listing records without their bodies is not logged. Bodies are not scanned for secrets a caller put into a prompt. |
| Compromised dependency or image | Cargo.lock and `--locked` everywhere, `npm ci`; `cargo audit`, `cargo deny` (licences, bans, sources; `deny.toml`) and `npm audit` in CI, weekly as well. CI writes an SPDX bill of materials of every image. A pushed version tag builds the images, pushes them to GHCR, signs them by digest with cosign (keyless) and attests their bill of materials. The Rust services run on distroless images pinned by digest, as an unprivileged user, with a read-only root and no capabilities. | Third-party images are pinned by tag, not digest; the console's base image too, and the tester's (`python:3.13-slim`) floats within its minor version. The tester's Python dependencies are locked (`uv.lock`) but not audited, and licences are checked for the Rust dependencies only. Nothing in `deploy/` checks a signature before an image runs: do it as the runbook shows (section 6). |
| A stolen or replayed console token (`PGW_AUTH=oidc`) | The core verifies a person's access token itself: pacod-id's signature (keys from its JWKS), the issuer (`PGW_ID_ISSUER`) and the audience `pacod-gw`; `pidt_` and imported `pgwa_` tokens are checked by introspection. Access tokens live five minutes. Every management instance follows pacod-id's feed and refuses a token whose session ended, whose account was disabled or deleted, or whose roles were taken, within two seconds (the end of a session, measured on the development stack with `gw-smoke revocation`: at most 3 ms over 20 samples). When its copy of the feed is older than 60 seconds (`PGW_ID_MAX_STALENESS`), or pacod-id does not answer, management calls are refused with 503 `identity_unavailable`; the data plane never asks. The console's own `pgws_` sessions are refused. | A token stays good until its session ends or it expires. While the feed is behind but younger than 60 seconds, a revocation can take that long to arrive. |
| The console's session cookie (`PGW_AUTH=oidc`) | pacod-id's tokens stay on the console's server side and travel to the browser only sealed: JWE with `dir` and A256GCM, under a key derived from `PGW_UI_SESSION_SECRET` (at least 32 characters) and the cookie's purpose, so a pending sign-in does not open as a session. The cookie is HttpOnly and SameSite=Lax, and `__Host-` (Secure, host-only) on https. Sign-in uses PKCE, `state` and `nonce` (`@pacod/id-sveltekit` with `@pacod/id-client`). | The cookie carries the session itself, so the console cannot delete it from the server: an ended session is cut off by pacod-id and by the core within two seconds, and the console then forgets the cookie. Whoever has `PGW_UI_SESSION_SECRET` can read and forge sessions of the console; changing it signs everyone out. |
| The gateway's database role reading pacod-id's tables | pacod-id has its own role, `pacod_id`, which is not a superuser and owns the database `pacod_id` (`deploy/scripts/create-id-role.sh`); `PUBLIC` has no rights on that database. | **Not closed.** The core connects as `pacod_gw`, which the PostgreSQL image makes a superuser, so a compromised core, or anyone with `POSTGRES_PASSWORD`, can read and change pacod-id's database in the same server: password hashes, sessions, sealed signing keys (sealed under `PID_KEK`, which the core does not hold). Mitigation, a change of its own: run pacod-id's database on another server, or demote the gateway's role to an ordinary owner of its database. |
| One-time values in logs | Caddy drops from its access logs the query parameters that carry one-time values: `token`, `next`, the sign-in's `code` and `state`, and on pacod-id's host `id_token_hint`, `login_hint` and `flow`; and the `Referer` and `Location` headers, which carry the same values (`deploy/caddy/Caddyfile`). Checked on the development stack: Caddy logged none. | A proxy of your own in front of Caddy must do the same. |
| The identity export file | `pacod-gw-core identity export` writes the users, admin tokens and role bindings with their Argon2id password hashes and token HMACs, and the invitations' link hashes, to a new file created with mode 0600; it refuses to overwrite one. The runbook (section 16) says to delete it after the import. | Whoever reads the file can guess passwords offline against the Argon2id hashes; the admin tokens' 256 bits make guessing them hopeless. It is as sensitive as a database dump. |
| Old admin tokens after the move | Imported `pgwa_` tokens keep working: pacod-id checks them with the gateway's pepper (`PID_LEGACY_PEPPERS=gw:<PGW_KEY_PEPPER>`), as the core did. They are service accounts at pacod-id and are revoked there like any other token. | pacod-id now holds `PGW_KEY_PEPPER`, which is also the HMAC key of the data plane's gateway keys: whoever reads pacod-id's environment or Secret can check guesses of gateway keys offline against a leaked `pacod_gw` database, as anyone holding the gateway's environment could before. |
| The core acting for its callers at pacod-id (`PGW_AUTH=oidc`) | For users, role bindings, admin tokens, members and invitations the core first applies its own role check, then calls pacod-id's admin API with a token exchanged from the caller's own (cached per caller), so pacod-id decides with the caller's own rights, on top of the gateway's check. The core's own client pushes the gateway's roles, registers organisations and workspaces, reads the feed and ends sessions at sign-out. | pacod-id trusts the core to present only tokens it received from callers: a compromised core can act for anyone who calls it, within that person's rights. It cannot act for someone who never called it. |
| Personal data after an account is deleted | When pacod-id deletes an account the core forgets it in one transaction (its copy, sessions, links) and its name in the audit log, template versions and invitations becomes "deleted account". A workspace's admins erase one user's usage events, audit records and end-user rollups with `POST /api/v1/orgs/{org}/workspaces/{ws}/erasure`; the audit log records that it happened, not whose. | Audit entries of invitations keep the invitee's address. A rollup run at the moment of an erasure can write a day's end-user row back. Hourly rollups carry no user and stay. |
| Abuse by an administrator | Roles from platform admin down to viewer; every configuration change is written to the audit log in the same transaction, with its actor and the hashes before and after. Logins and failed logins, key re-encryption and audit-record reads are logged too. | The audit log is an ordinary table: a database administrator can change it. Ship it elsewhere if that matters. |

## Not covered by the gateway

- The host, the cluster and their administrators.
- TLS between the services inside the stack; Caddy terminates TLS at the edge.
- Denial of service beyond the per-key throttles, concurrency caps and body limits.
- Secrets that callers put into prompts.
